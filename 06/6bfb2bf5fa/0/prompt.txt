**Direct answer first:** do **not** make a Databricks-hosted interpreter agent the critical path for this build on Free Edition. An external process can call Databricks Foundation Model APIs when a compatible endpoint/model is available and you have a workspace host plus Databricks API token, but Free Edition’s endpoint/model availability and quota limits make this an unreliable two-hour dependency. Treat it as an optional, manually invoked enrichment step—not something your deterministic remediation workflow requires to function. [docs.databricks](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations)

Your architecture is sensible **only if “three agents” really means two bounded LLM steps around a deterministic core**: policy interpretation before graph analysis, and code execution after a reviewed work order. Do not add a Databricks “supervisor” or conversational orchestration layer. The deterministic graph and post-change re-analysis should remain the authority.

## Bottom-line architecture

The best shape is a **human-gated deterministic pipeline**, not an autonomous multi-agent system:

```text
Natural-language policy
        │
        ▼
Databricks Interpreter (optional, structured extraction only)
        │
        ▼
Human approval / canonical dependency mapping lookup
        │
        ▼
Offline Go CLI: PivotMap
  - no network
  - no model
  - source-linked evidence
  - JSON work order
        │
        ▼
External coding agent: Executor
  - edits direct violations only
  - writes implementation evidence
  - commits
        │
        ▼
Offline Go CLI rerun
  - invalidated count must decrease
  - diff before vs. after
  - no LLM grade
        │
        ▼
Delta history / Databricks analytics
  - optional, asynchronous
```

The key correction is this:

- **Interpreter:** may propose identifiers.
- **Canonical mapping or human reviewer:** authorizes identifiers.
- **PivotMap:** establishes graph-supported impact facts.
- **Executor:** makes constrained edits.
- **Rerun:** independently verifies whether the direct detected violation was removed.

Do not let the interpreter decide whether a library handles customer data, whether a policy applies to a package, or whether remediation is complete. Those are governance decisions or deterministic verification outcomes, respectively.

## Best starting point

**Single best starting point: call a Databricks Foundation Model API from a small Python script or local service, request JSON-only policy extraction, validate it with Pydantic/JSON Schema locally, and persist the input/output plus approval decision into a Delta table.**

Why this is the best starting point:

- It proves the only essential Databricks-specific part: externally callable hosted inference.
- It avoids deploying a custom agent endpoint, Agent Bricks, Lakebase, Apps, multi-agent supervision, MCP, and retrieval infrastructure.
- It gives you a real audit record.
- It can feed your existing offline CLI with an exact package list.
- If endpoint access, quota, auth, or model availability fails, your architecture can fall back to a manually approved mapping file without breaking the core workflow.

Databricks Foundation Model APIs are documented as OpenAI-compatible and callable through the OpenAI client, REST API, Foundation Models APIs SDK, or MLflow Deployments SDK; requests authenticate using a Databricks API token. [docs.databricks](https://docs.databricks.com/aws/en/machine-learning/foundation-model-apis/)

Most “end-to-end agent” tutorials implicitly assume more than a Free Edition proof-of-concept:

- A model endpoint or available Foundation Model API.
- An experiment and permissions sufficient to log traces.
- Often a serving endpoint for deployment.
- A workspace region where the model and relevant preview/GA feature are available.
- Enough quota that retries and first-run initialization do not exhaust the day’s allocation.

For your architecture, begin with one **external client → Foundation Model API** invocation, no custom serving endpoint and no deployed agent.

### What the evidence implies for your design

Your use case avoids the worst form of multi-agent coordination because the agents should not deliberate, negotiate, or share mutable reasoning state.

Use a **linear, typed, durable handoff**:

```text
Interpreter output:
  policy_interpretation/v1 JSON

PivotMap output:
  pivot_work_order/v1 JSON

Executor output:
  remediation_execution/v1 JSON

Verifier output:
  pivot_verification/v1 JSON
```

Each handoff must include:

- `schema_version`
- `request_id`
- `repository`
- `commit_sha`
- `tool_version`
- `input_hash`
- `created_at`
- `actor`
- `policy_text`
- `approved_identifiers`
- `confidence`
- `known_unknowns`
- `source_evidence`
- `validation_commands`
- `result`

This makes the architecture closer to a reliable distributed workflow than a chat among autonomous agents.

# G. Multi-agent orchestration research

## Official Databricks support

Databricks supports building custom agents and integrating tools, including MCP, Unity Catalog functions, and third-party authoring libraries. It also documents integrations with LangChain/LangGraph and OpenAI/Anthropic tool patterns. [docs.databricks](https://docs.databricks.com/aws/en/generative-ai/mcp)

However, that does **not** mean your system needs a native multi-agent supervisor.

### What is sensible

Use a fixed state machine:

```text
PENDING_INTERPRETATION
  → AWAITING_HUMAN_APPROVAL
  → ANALYZED
  → AWAITING_EXECUTION
  → EXECUTED
  → VERIFIED
  → CLOSED | ESCALATED
```

The “orchestrator” can be ordinary workflow code, a CI pipeline, or a Databricks Workflow/job later. It does not need an LLM.

### What is not sensible

Do not use:

- An LLM supervisor to decide whether the policy is valid.
- An LLM to select which direct violation should be changed.
- An LLM to evaluate whether the executor’s change passes policy.
- A debate between interpreter and executor.
- A multi-agent memory layer for a one-shot policy interpretation.

Those add non-determinism where you already have better controls: reviewer approval, static evidence, tests, and independent post-change analysis.

## MCP and A2A

### MCP

MCP is relevant, but not essential for your first build.

Databricks documents MCP support for connecting agents to tools, data, and workflows. Managed and external MCP servers can use Unity Catalog permissions, and UC functions can be surfaced through a managed MCP endpoint shaped like:

```text
https://<workspace-hostname>/api/2.0/mcp/functions/<catalog>/<schema>
```

A specific function may be appended to that path. [docs.databricks](https://docs.databricks.com/aws/en/agents/custom-agents/create-custom-tool)

A reasonable future MCP tool would be:

```text
resolve_policy_packages(
  policy_text: string,
  repository_language: string,
  ecosystem: string
) -> {
  candidates: [...],
  canonical_matches: [...],
  review_required: boolean
}
```

But for your architecture, **the local CLI should not become an MCP tool that makes it callable by arbitrary agents unless you preserve its local/no-egress boundary and access controls**. The executor can simply read a plan file.

### A2A

I found no official, verifiable Databricks documentation in the available search results establishing a general Agent-to-Agent protocol as the recommended interoperability layer for an external coding agent and a Databricks agent.

Use:

- JSON artifacts for durable workflow handoffs.
- MCP for tool access when it materially helps.
- Standard HTTPS/REST for invoking models or APIs.
- Git commits and Entire checkpoints for executor provenance.

Do not claim A2A interoperability unless you identify a current official product document for your cloud/workspace and validate feature access.

## LangGraph, OpenAI Agents SDK, CrewAI

| Framework | Fit for your architecture | Databricks relevance | Recommendation |
|---|---|---|---|
| Native Agent Framework / custom agent | Good if you later deploy a governed interpreter with tracing, tools, evaluations, and serving | GA framework/evaluation and integrated MLflow/UC governance | Use only after the simple external model-call proof works |
| LangGraph | Technically compatible, especially if you later need resumable state or complex human approval | Databricks documents LangChain/LangGraph integration with UC tools | Overkill for one interpreter step |
| OpenAI Agents SDK | Can use compatible hosted model APIs and typed tools | Lakebase docs mention Apps support for OpenAI Agents SDK-backed memory | Unnecessary unless you already standardize on it |
| CrewAI | Possible through generic model/API connectivity | No compelling Databricks-native advantage surfaced here | Avoid for this use case |
| Agent Bricks | Useful for enterprise-supported optimized agents and richer data-connected tasks | Current platform product for agent construction/governance | Avoid for a two-hour single-purpose extraction agent |

The native framework is preferable only when you need Databricks-native deployment, trace/evaluation workflows, governed data tools, and lifecycle controls. For a single structured classification call, it is complexity without proportional benefit.

## External invocation: exact practical model

The documented model-call premise is:

1. Identify your Databricks workspace host:
   ```text
   https://<workspace-hostname>
   ```

2. Obtain an API token with the permissions required to invoke the model endpoint.

3. Invoke via an OpenAI-compatible client, Databricks REST API, Foundation Models APIs SDK, or MLflow Deployments SDK.

4. Specify the available model/endpoint as the `model` value.

Databricks states Foundation Model APIs require a Databricks API token and are OpenAI-compatible. [docs.databricks](https://docs.databricks.com/aws/en/machine-learning/foundation-model-apis/)

A typical OpenAI-compatible Python pattern is conceptually:

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["DATABRICKS_TOKEN"],
    base_url=f"{os.environ['DATABRICKS_HOST']}/serving-endpoints",
)

response = client.chat.completions.create(
    model=os.environ["DATABRICKS_MODEL"],
    messages=[
        {
            "role": "system",
            "content": (
                "Return only JSON matching the supplied schema. "
                "Never return prose or Markdown."
            ),
        },
        {
            "role": "user",
            "content": policy_text,
        },
    ],
)
```

**Important:** endpoint paths and model naming vary by current Databricks API version and the exact Foundation Model API/model endpoint available in a workspace. Do not copy that skeleton into production without verifying it against the current Foundation Model API documentation and your workspace’s available endpoints. The official source confirms OpenAI compatibility but the available search excerpt does not provide an authoritative full code block or exact endpoint path for every model type. [docs.databricks](https://docs.databricks.com/aws/en/machine-learning/foundation-model-apis/)

### Minimum proof before committing architecture

Run this acceptance test first:

```text
Given:
  - a Free Edition workspace
  - a token
  - one candidate hosted model

Prove:
  1. A process outside Databricks can authenticate.
  2. It can make one model request.
  3. The response arrives before your local timeout.
  4. A local JSON Schema validator accepts it.
  5. You can repeat it without immediately hitting rate/quota failure.
```

If any step fails, do not debug an agent framework. Use the fallback path:

```text
Natural-language policy
  → human reviewer selects canonical package IDs
  → checked-in mapping JSON
  → deterministic PivotMap
```

That fallback still demonstrates the core architecture and is often more governance-correct.

## Reliable structured output

### Do not rely only on prompting

“Return JSON only” is not reliable enough for governance-sensitive package mapping.

Use three layers:

1. **Native structured output / JSON schema or tool/function calling**, if the specific available Databricks model endpoint supports it.
2. **Local schema validation** after receiving the response.
3. **Human approval or canonical mapping resolution** before PivotMap runs.

The output schema should be intentionally narrow:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "PolicyInterpretationV1",
  "type": "object",
  "additionalProperties": false,
  "required": [
    "policy_text",
    "proposed_targets",
    "ambiguities",
    "requires_human_approval"
  ],
  "properties": {
    "policy_text": {
      "type": "string",
      "minLength": 1
    },
    "proposed_targets": {
      "type": "array",
      "minItems": 1,
      "maxItems": 20,
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": [
          "identifier",
          "ecosystem",
          "target_kind",
          "confidence",
          "rationale"
        ],
        "properties": {
          "identifier": {
            "type": "string",
            "minLength": 1,
            "maxLength": 256
          },
          "ecosystem": {
            "type": "string",
            "enum": ["go", "python", "java", "javascript", "other", "unknown"]
          },
          "target_kind": {
            "type": "string",
            "enum": ["package", "module", "library", "namespace", "unknown"]
          },
          "confidence": {
            "type": "number",
            "minimum": 0,
            "maximum": 1
          },
          "rationale": {
            "type": "string",
            "maxLength": 500
          }
        }
      }
    },
    "ambiguities": {
      "type": "array",
      "items": {
        "type": "string"
      }
    },
    "requires_human_approval": {
      "type": "boolean"
    }
  }
}
```

Then impose a local policy:

```text
If JSON fails schema validation → reject.
If ecosystem is unknown → reject.
If any identifier is not in the repository’s dependency inventory → flag for review.
If confidence < threshold → require review.
If multiple candidates exist → require review.
If policy says “customer data” but graph has no data-flow certainty → annotate, do not claim enforcement.
```

### Canonical mapping should be a table, not an LLM memory

A Unity Catalog function can support canonical mapping, but the canonical source should be a governed Delta table such as:

```text
governance.policy_dependency_mapping
```

| policy_concept | ecosystem | identifier | status | owner | evidence_url | approved_at | expires_at |
|---|---|---|---|---|---|---|---|
| customer-data-egress | go | `net/http` | approved | security-team | policy reference | timestamp | timestamp |
| customer-data-egress | go | `github.com/acme/telemetry` | approved | security-team | policy reference | timestamp | timestamp |

A UC SQL function can wrap a deterministic lookup:

```sql
resolve_policy_packages(policy_concept STRING, ecosystem STRING)
```

This is useful because UC functions are governed, shareable, and can be exposed as agent tools; Databricks specifically recommends UC functions for known structured retrieval where the agent supplies parameters. [docs.databricks](https://docs.databricks.com/aws/en/agents/custom-agents/create-custom-tool)

But it should **not** be a free-form “policy text → package” function unless you deliberately maintain a mapping taxonomy. An LLM may classify the policy language, but a governed lookup should resolve the approved targets.

## Governance, audit, and provenance

## Audit design

For each interpretation, persist a first-class immutable record:

```json
{
  "interpretation_id": "uuid",
  "created_at": "timestamp",
  "requestor": "identity",
  "repository": "org/repo",
  "commit_sha": "sha",
  "policy_text": "we can no longer send customer data through Library X",
  "model_provider": "databricks",
  "model_name": "exact configured identifier",
  "prompt_template_version": "interpreter-v1",
  "schema_version": "policy_interpretation/v1",
  "raw_response": "exact raw body, access-controlled",
  "validated_response": {
    "proposed_targets": []
  },
  "canonical_mapping_version": "mapping-table snapshot/version",
  "approval_status": "approved|rejected|needs_review",
  "approved_targets": [],
  "approver": "identity",
  "approval_at": "timestamp",
  "pivot_plan_id": "uuid",
  "work_order_uri": "durable artifact reference",
  "verification_result": "pass|fail|partial"
}
```

The minimum reviewer replay must be possible from:

- Exact policy wording.
- Prompt template version.
- Exact model identifier.
- Model parameters, including temperature and seed if supported.
- Exact raw response.
- Schema-validation result.
- Mapping-table version/snapshot.
- Reviewer approval decision.
- Repo commit SHA.
- Graph snapshot/tool version.
- Generated plan hash.
- Executor commit SHA.
- Verification rerun result.

### Reproducibility caveat

You can make an interpretation **auditable and replayable**, but you cannot promise bit-for-bit LLM reproducibility across model version changes, provider updates, non-deterministic serving, or unavailable seeds.

The appropriate claim is:

> “We preserve the original evidence and decision context so a reviewer can audit it. Replays are comparative evaluations, not proof that a hosted model will regenerate identical output.”

MLflow Tracing is useful because it records agent/application inputs, outputs, intermediate steps, and metadata. Databricks recommends Unity Catalog-backed trace storage for new production workloads; these traces can be stored as governed OTel Delta tables and queried through SQL. [docs.databricks](https://docs.databricks.com/aws/en/mlflow3/genai/tracing/)

### MLflow evaluation

For the interpreter, create a small curated evaluation dataset:

| policy_text | repo ecosystem | allowed identifiers | forbidden identifiers | reviewer-approved expected result |
|---|---|---|---|---|
| “No customer data through Library X” | Go | `library/x` | unrelated packages | target list + `requires_human_approval=true` |
| “Ban deprecated HTTP package” | Go | package path | similarly named package | exact target only |
| “Do not use analytics SDK Y in production” | Python | module path | test-only mock package | target list plus scope annotation |

Score at least:

- JSON schema valid: deterministic Boolean.
- Identifiers parse in the ecosystem: deterministic Boolean.
- Identifiers occur in dependency inventory: deterministic Boolean.
- Approved-target precision/recall: deterministic against reviewer labels.
- Unsupported inference count: reviewer metric.
- False policy-to-package mapping rate: reviewer metric.
- Human approval override rate: governance metric.

Do **not** score it with an LLM judge as the only standard. Your domain is perfectly suited to deterministic and human-reviewed metrics.

## Analytics: genuine second use

The analytics layer is legitimate if it answers questions the one-off CLI cannot:

- Which prohibited dependencies recur across repositories and time?
- Which policies generate the largest direct remediation burden?
- Which packages produce large downstream blast radii?
- Which directories repeatedly become `UNREACHED` due to parser coverage gaps?
- How often does the interpreter require human override?
- How often does the executor reduce `INVALIDATED` to zero on the first attempt?
- Which policy categories correlate with slow remediation?

### Example queries

**Policies with most direct remediation work:**

```sql
SELECT
  policy_id,
  prohibited_identifier,
  COUNT(*) AS direct_violating_files,
  COUNT(DISTINCT repository) AS repositories
FROM analysis.pivot_file_verdicts
WHERE verdict = 'INVALIDATED'
GROUP BY policy_id, prohibited_identifier
ORDER BY direct_violating_files DESC;
```

**Repeat-offender files:**

```sql
SELECT
  repository,
  path,
  COUNT(DISTINCT pivot_run_id) AS violation_events,
  COUNT(DISTINCT prohibited_identifier) AS distinct_constraints
FROM analysis.pivot_file_verdicts
WHERE verdict = 'INVALIDATED'
GROUP BY repository, path
HAVING COUNT(DISTINCT pivot_run_id) > 1
ORDER BY violation_events DESC;
```

**Blast-radius trend:**

```sql
SELECT
  date_trunc('month', observed_at) AS month,
  prohibited_identifier,
  AVG(CASE WHEN verdict = 'AT_RISK' THEN 1 ELSE 0 END) AS average_at_risk_per_row,
  COUNT_IF(verdict = 'INVALIDATED') AS invalidated_files,
  COUNT_IF(verdict = 'UNREACHED') AS coverage_gaps
FROM analysis.pivot_file_verdicts
GROUP BY 1, 2
ORDER BY 1, 2;
```

### Genie: useful later, not now

Genie is a plausible analyst interface once the Delta tables exist:

> “Which policy produced the largest production blast radius in the past 90 days?”

> “Which repositories have the highest share of `UNREACHED` files under customer-data egress policies?”

> “Which mappings did reviewers override most often?”

Genie Conversations can be invoked programmatically; the API documentation exposes Genie conversation endpoints and requires the `genie` API scope. Databricks’ announcement says the API can embed Genie into other apps and agents, and 2026 release notes indicate Conversation API GA. [docs.databricks](https://docs.databricks.com/api/genie/v1)

But a Genie Space is not part of the remediation control plane. It is an **analytics and discovery surface**. Do not let Genie choose package identifiers or approve work orders.

## Lakebase: what it is and whether you need it

Lakebase is a managed Postgres operational database integrated with Databricks, positioned for transactional application state, agent memory, configuration, and real-time decisioning. It supports short-term conversation state and long-term agent memory; the current documentation describes integration with Databricks Apps and Model Serving, including LangGraph checkpointers and OpenAI Agents SDK support. [docs.databricks](https://docs.databricks.com/aws/en/oltp/projects/state-management)

For your architecture:

| Use case | Lakebase fit |
|---|---|
| Single policy interpretation → approved work order | No; a Delta table or artifact file is enough |
| Durable reviewer queue with status transitions | Maybe, but Delta plus a simple App is enough initially |
| Conversational, stateful policy-review assistant | Yes, later |
| Multi-turn supervisor coordinating many remediation jobs | Maybe, but only after proving need |
| Canonical policy-to-package mappings | Usually no; Delta/UC table is better for analytical governance |
| Session memory for executor | No; Git commit, work order, and Entire checkpoint are better sources of truth |

**Verdict:** do not use Lakebase in your first iteration. It adds a stateful operational data plane to a workflow that should be deliberately stateless and artifact-driven.

## Databricks Apps reviewer UI

A reviewer-facing App can be valuable after you have stored interpretation/work-order rows:

- Display original policy text.
- Show candidate packages and canonical mapping matches.
- Show relevant dependency inventory.
- Show direct violations and graph evidence.
- Let a reviewer approve/reject/modify the concrete targets.
- Generate an immutable approved work order.
- Link the executor commit and post-execution verification run.

The App should not render giant graph dumps. Its central review object should be:

```text
Policy → proposed targets → approved targets → direct violation roots
→ evidence → execution state → verification result
```

On Free Edition, Apps are limited and auto-stop when idle per the constraints you supplied. That is acceptable for a reviewer demo, but it is not a dependable always-on enterprise approval service. The Free Edition limitations document confirms quota-limited Apps as part of the environment constraints. [docs.databricks](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations)

## Known setup traps

### 1. Confusing Foundation Model APIs with custom serving

A hosted foundation model call and a custom Model Serving endpoint are not the same setup path. The latter adds deployment, endpoint lifecycle, permission, and quota complexity. Foundation Model APIs are the fastest viable external-call path. [docs.databricks](https://docs.databricks.com/aws/en/machine-learning/foundation-model-apis/)

### 2. Assuming a model is available everywhere

Databricks documents supported regions and model availability constraints. Free Edition further limits which models/endpoints are available. Confirm the exact model in your actual workspace before writing integration code. [docs.databricks](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations)

### 3. Treating Free Edition as a reliable CI dependency

Do not put quota-limited hosted inference in a production CI gate. A quota exhaustion or temporary endpoint unavailability should not stop deterministic remediation analysis. Keep the interpreter asynchronous and cache approved interpretations.

### 4. Mixing API-token identity with governance identity

For audit, record:

- who submitted the policy;
- which service principal or PAT invoked the model;
- which reviewer approved targets;
- which agent/executor authored the commit.

Do not collapse these into “the agent did it.”

### 5. Logging secrets or sensitive source context

Store the original policy and model output carefully. Avoid sending repository source indiscriminately to the interpreter. Your interpreter should need the policy text plus a compact local dependency inventory, not proprietary source code.

### 6. Claiming structured output guarantees correctness

Schema validity only proves shape. It does not prove that `Library X` maps to the right Go module path, or that a package actually handles customer data. Require canonical mapping and approval where consequences matter.

### 7. Graph false negatives

Your own observed interface-dispatch failure is central. `SAFE` means:

> “No path was detected under this parser, graph, relation set, and analysis snapshot.”

It must never mean:

> “Proven policy compliant.”

Make this statement part of every work order and reviewer UI.

## Is the three-agent architecture sensible?

## The case for it

Yes—**as a typed, linear workflow**, it cleanly separates fundamentally different kinds of work:

- The interpreter handles ambiguous human policy language.
- PivotMap handles deterministic structural reasoning and evidence extraction.
- The executor handles code modification.
- The verifier independently checks graph-supported outcomes.

This separation is excellent governance design because it prevents the executor from reinterpreting policy and prevents an LLM from grading its own changes. It also yields a strong provenance chain:

```text
Policy wording
→ interpreted targets
→ approved targets
→ graph evidence
→ bounded code edits
→ commit/checkpoint
→ independent verification
```

Databricks contributes real value if you need:

- Centralized model access and identity controls.
- MLflow trace retention and evaluation.
- Unity Catalog-governed canonical policy mappings.
- Delta analytics across many repositories/work orders.
- Reviewer workflow at organizational scale.
- Genie-based exploration of accumulated remediation history.

## The case against it

For a small system or hackathon, Databricks is likely unnecessary complexity.

The interpreter is a single structured extraction/classification call. It does not require:

- A deployed agent.
- Agent Bricks.
- Lakebase memory.
- A multi-agent supervisor.
- LangGraph/CrewAI.
- MCP.
- A reviewer App.
- Genie.

The Databricks overhead is real:

- Workspace/auth/token setup.
- Model and region availability uncertainty.
- Free Edition daily quota risk.
- Endpoint semantics and SDK version drift.
- Auditing setup that is more involved than writing immutable artifacts.
- Vendor lock-in around serving, UC governance, and trace storage.
- Latency from an external model call in a workflow otherwise designed to be local and deterministic.

Research also supports avoiding gratuitous multi-agent architecture: multi-agent systems often show small gains over strong single-agent baselines and introduce specification, coordination, and verification failures. Your design avoids much of that only if the agents are not free-form collaborators. [iclr](https://iclr.cc/virtual/2025/33314)

## Verdict

**Build the architecture as “one optional hosted interpreter + deterministic core + one external executor + deterministic verifier,” not as a Databricks-native three-agent system.**

For now:

- Keep the policy interpreter behind an interface.
- Make its output an auditable, versioned JSON artifact.
- Support a human-approved mapping-file fallback.
- Keep PivotMap entirely local and no-egress.
- Keep executor integration separate from Databricks.
- Store results in Delta only once you have enough runs to analyze.
- Add MLflow tracing, UC functions, Apps, Genie, Lakebase, MCP, and Agent Bricks only when there is a demonstrated organizational need.

That preserves the compelling part of your architecture—deterministic, evidence-backed remediation—without making an unavailable or quota-exhausted model endpoint a single point of failure.

## Follow-up research topics

1. **Databricks Free Edition live endpoint validation:** Verify your exact workspace region, available Foundation Model API models, token scopes, and external-call behavior before spending implementation time on agent frameworks.

2. **Policy-to-package canonicalization design:** Define the governed mapping schema, ownership, review lifecycle, expiry, and how policies map differently across Go modules, Python distributions/imports, Java Maven coordinates, and JavaScript packages.

3. **Deterministic policy verification extensions:** Research how to combine import/call graph evidence with package manifests, SBOMs, taint/data-flow analysis, and test execution without overstating compliance.

4. **Evaluation corpus for policy interpretation:** Build a labeled set of real historical policies, intended dependency targets, ambiguous cases, and reviewer overrides to measure interpreter precision, recall, schema compliance, and unsafe inference rate.

5. **Repository-scale remediation analytics:** Design Delta schemas and metrics for blast radius, direct-violation recurrence, `UNREACHED` coverage debt, work-order completion time, and verification-first-pass success.
