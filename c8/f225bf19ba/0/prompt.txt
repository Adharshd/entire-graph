THE TRAP — READ THIS TWICE
PivotMap's existing thesis is already "graph is evidence, not an oracle": it has UNREACHED, it prints
"SAFE means no path found", it ships known_blind_spots. The tempting response is "we already did
this." That scores in the PARTIAL band, because the rubric wants a clear statement of which
assumption the curveball INVALIDATED. Claiming nothing changed means no adaptation to score.

THE ASSUMPTION THAT WAS ACTUALLY INVALIDATED (verify this, do not take it on trust)
Uncertainty is tiered at the LANGUAGE level (semantic vs inventory-only) but NOT at the EDGE level.
Inside Go these two are rendered identically and treated identically by the classifier:
    IMPORTS os/exec         confidence 1.00   <- a fact
    CALLS   regexp.go       confidence 0.68   <- "matched globally unique method name", a heuristic
A P0 work item can rest entirely on the second, and nothing says so. Confidence is carried through
the whole pipeline and never used to affect a verdict, a priority, an action, or the plan.

STRONGEST SUSPECTED FINDING — CONFIRM IT IN SOURCE FIRST

snapshot.Header.PartialFailures into the response but appears never to consult them when assigning a
verdict. Meanwhile `entire graph impact` self-reports "Completeness: degraded for Go" with
W_DATA_FLOW_EVIDENCE_UNMERGED. If that holds, SAFE currently conflates "fully parsed, no path found"
with "the parser had diagnostics here, and no path found" — which is exactly the distinction the card
demands. Verify against source before claiming it.
